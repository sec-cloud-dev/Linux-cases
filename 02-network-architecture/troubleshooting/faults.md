# Разбор поломок

Порядок — тот, в котором я их находил, а не тот, в котором они были внесены. Таймкоды указаны по смонтированной записи.

---

## 1. Снесена таблица `nat` на dev-router

**Симптом.** Из `client1` шлюз `192.168.10.1` отвечает, `10.200.0.2` отвечает, а хост `10.200.0.1` — 100% потерь. Таймаут, не отказ.

**Локализация.** Сужение пингом даёт границу: до ближнего конца роутера доходим, дальше нет. Значит смотрю роутер. `ip_forward` = 1, форвардинг включён. А `nft list ruleset` пуст.

**Причина.** Без masquerade на `veth-dev` пакеты из `192.168.10.0/24` приходят к хосту с исходным адресом из этой сети. Хост маршрутизирует ответ по своим правилам — и ответ уходит не туда, откуда пришёл запрос.

**Фикс.**
```bash
ip netns exec dev-router nft add table ip nat
ip netns exec dev-router nft add chain ip nat postrouting \
  '{ type nat hook postrouting priority srcnat; policy accept; }'
ip netns exec dev-router nft add rule ip nat postrouting oifname "veth-dev" masquerade
```

После фикса пинг пошёл сразу, `ttl=63` — один хоп через роутер.

## 2. `veth-b1` с MTU 1300

**Симптом.** Малые пакеты ходят нормально, 30 пингов подряд без потерь. А `ping -M do -s 1452` выдаёт:
```
ping: sendmsg: No buffer space available
```

**Локализация.** Ошибка **локальная** — пакет даже не ушёл. Это не ICMP с пути и не таймаут: ядро отказалось отправлять, потому что запрошенный размер больше MTU интерфейса, а фрагментация запрещена флагом `DF`.

Внутри `client1` интерфейс с MTU 1500, значит смотрю хостовую сторону:
```bash
ip a | grep veth
```
```
18: veth-b1@if17: ... mtu 1300
23: veth-of@if22: ... mtu 1300
```

**Причина.** MTU моста равен минимуму по его портам, поэтому порезанный MTU одного интерфейса просаживает всё плечо, а не только себя.

**Фикс.**
```bash
ip link set veth-b1 mtu 1500
ip link set veth-of mtu 1500
```

**Важная оговорка.** Скрипт режет MTU **только на одном** интерфейсе. Второй накопился с предыдущих прогонов и `verify.sh` его не ловил, потому что MTU в эталон не входит. То есть из двух исправленных интерфейсов одна — поломка из восьми, вторая — незамеченный дрейф. Это дырка в проверке, и она записана в бэклог.

**Проверка.** Не пингом по 64 байта, а большим пакетом с `DF` — и наружу, и до сканера:
```bash
ip netns exec client1 ping -M do -s 1452 -c 3 8.8.8.8
ip netns exec client1 ping -M do -s 1452 -c 3 192.168.10.100
```

## 3. Удалён `10.0.0.0/24` из таблицы `t_dev`

**Симптом.** Из `office1` шлюз `10.0.0.5` отвечает, а хост `10.200.0.1` — 100% потерь.

**Локализация — самая интересная в прогоне.** Первым делом проверяю, доходит ли запрос до хоста:
```bash
ip route get 10.200.0.1 from 10.0.0.10 iif br-office
```
```
local 10.200.0.1 from 10.0.0.10 dev lo table local
```
Хост признаёт пакет своим и принимает локально. Значит путь **туда** цел, и теряется **ответ**.

Дальше вопрос: по какой таблице пойдёт ответ? У него источник `10.200.0.1`, а значит сработает правило `32765: from 10.200.0.0/30 lookup t_dev`. Дифаю её:
```bash
diff <(ip route show table t_dev) /root/etalon/t_dev.txt
```
```
1a2
> 10.0.0.0/24 dev br-office scope link
```
`>` — строка есть в эталоне, у меня нет. Маршрут удалён.

**Причина.** Без него лукап в `t_dev` не находит совпадения для `10.0.0.10`, падает на `default via 192.168.31.1 dev enp0s3` — и ответ офису уходит в интернет.

Ключевой момент: правило PBR сопоставляется с **уже сформированным** пакетом. Сначала ядро решает, с какого адреса отвечать (берёт адрес интерфейса, на котором принят запрос — здесь `10.200.0.1`), и только потом по этому адресу выбирает таблицу. Поэтому PBR применяется и к трафику, который хост порождает сам, а не только к транзиту.

**Фикс.**
```bash
ip route replace 10.0.0.0/24 dev br-office scope link table t_dev
```

## 4. Лишний `10.0.0.0/25` в таблице `main`

**Симптом.** Хост из офиса теперь отвечает, а интернета из офиса нет.

**Локализация.** Маршрут наружу проверяю первым делом:
```bash
ip route get 8.8.8.8 from 10.0.0.10 iif br-office
```
```
8.8.8.8 from 10.0.0.10 via 192.168.31.1 dev enp0s3 table t_office
```
Путь туда правильный. Значит снова обратный. Ответ от `8.8.8.8` после un-NAT адресован `10.0.0.10`, источник внешний — под правила PBR не попадает, идёт по `main`:
```bash
ip route show table main
```
```
10.0.0.0/25 via 10.200.0.2 dev veth-host     ← лишний
10.0.0.0/24 dev br-office proto kernel scope link src 10.0.0.5
```

**Причина.** Та же механика, что в поломке 3, но на уровне `main`: `10.0.0.10` попадает и в `/24`, и в `/25`, а при поиске маршрута выигрывает более длинный префикс. Ответ уходил на роутер вместо офисного моста. Запрос доходил, ответ терялся — ровный таймаут.

**Фикс.**
```bash
ip route del 10.0.0.0/25 table main
```

Сразу после этого офис пошёл в интернет и DNS заработал.

## 5. Снято правило DNAT на сканер

**Симптом.** Из офиса `192.168.10.100` не пингуется и `:8080` не отвечает.

**Локализация.** Сначала проверил фаервол в самом офисном неймспейсе — пуст. Значит хост:
```bash
dnft
```
```
45a46
> ip saddr 10.0.0.0/24 tcp dport 8080 dnat to 192.168.10.100:8080
```
`>` — правило есть в эталоне, у меня нет.

**Причина.** Без DNAT запросы из офисного сегмента на `:8080` не перенаправляются на сканер.

**Фикс.**
```bash
nft add rule ip nat prerouting ip saddr 10.0.0.0/24 tcp dport 8080 dnat to 192.168.10.100:8080
```

Сканер всё равно не ответил — значит поломок на этом пути больше одной. Так и оказалось: 6 и 7.

**Замечание к самому правилу.** У него нет `ip daddr`, то есть под перенаправление попадает любой адрес назначения на порту 8080, а не только шлюз. Воспроизведено как в эталоне, но правило переширокое. Сужение — в бэклоге.

## 6. Удалён маршрут по умолчанию в контейнере

**Симптом.** Из офиса сканер недоступен, из `client1` — доступен.

**Локализация.** Эта пара симптомов сама указывает на причину. `client1` и сканер сидят в одном сегменте `192.168.10.0/24` на мосту `br0`, им маршрут не нужен — общаются напрямую на L2. А офис в другой сети, и чтобы ответить ему, контейнеру нужен маршрут наружу.

```bash
pid=$(docker inspect -f '{{.State.Pid}}' bucket-scanner)
nsenter -t "$pid" -n ip route
```
```
192.168.10.0/24 dev eth proto kernel scope link src 192.168.10.100
```
Только локальная сеть, `default` нет.

**Фикс.**
```bash
nsenter -t "$pid" -n ip route add default via 192.168.10.1
```

Заодно проверил сокет — `ss -tulpn` показал `0.0.0.0:8080`, с сервисом порядок.

## 7. Чужая таблица nftables в контейнере, drop на 8080

**Симптом.** После фикса 6 офис всё ещё получает таймаут. Причём `curl -v` показывает, что соединение даже не устанавливается.

**Локализация.** Таймаут, а не `Connection refused` — значит порт не закрыт, пакеты просто исчезают. Сервис слушает, маршрут есть, остаётся фаервол внутри контейнера:
```bash
nsenter -t "$pid" -n nft list ruleset
```
```
table inet filter {
        chain input {
                type filter hook input priority filter; policy accept;
                tcp dport 8080 counter packets 5 bytes 300 drop
        }
}
```
Счётчик 5 пакетов — правило срабатывало прямо во время диагностики.

**Причина.** Входящие SYN на порт 8080 дропаются до того, как доберутся до сокета. Сервис их не видит и ничего не отвечает, отсюда тишина вместо RST.

**Фикс.**
```bash
nsenter -t "$pid" -n nft delete table inet filter
```

Сразу после этого `curl` из офиса отдал 200 и листинг каталога.

**Проверка под нагрузкой.** 50 МБ из обоих сегментов:
```
client1: 200 52428800 0.034s
office1: 200 52428800 0.086s
```

## 8. `veth1-peer` выпал из бонда

**Симптом.** Отсутствует. Вся сеть работает: связность, интернет, DNS, HTTP, 50 МБ. Первый полный прогон `verify.sh` показал единственную красную строку:
```
FAIL bond0: слейвов 1 из 2
```

**Локализация.**
```bash
ip netns exec dev-router cat /proc/net/bonding/bond0
```
В бонде только `veth2-peer`. Для сравнения хостовый бонд — там оба слейва, но `veth1` в состоянии `MII Status: down`, что подтверждает: разрыв на дальнем конце пары.

Дифф конфига бонда при этом чистый — `miimon 100`, режим `active-backup`. То есть опрос линков работает, проблема не в нём:
```bash
diff <(ip netns exec dev-router sed -n '/Bonding Mode\|MII Polling\|Up Delay\|Down Delay/p' \
  /proc/net/bonding/bond0) /root/etalon/bond0.txt
```

Смотрю флаги интерфейса:
```bash
ip netns exec dev-router ip a
```
```
9: veth1-peer@if10: <BROADCAST,MULTICAST> mtu 1500 ... state DOWN
11: veth2-peer@if12: <BROADCAST,MULTICAST,SLAVE,UP,LOWER_UP> ... master bond0
```
У `veth1-peer` нет флага `SLAVE` и нет `master bond0` — он вынут из бонда. Побочный эффект: когда слейв освобождают командой `nomaster`, ядро опускает интерфейс, поэтому он ещё и `DOWN`.

**Фикс.**
```bash
ip netns exec dev-router ip link set veth1-peer master bond0
ip netns exec dev-router ip link set veth1-peer up
```

**Почему это важная поломка.** Функционально ничего не ломается — трафик идёт через оставшийся слейв. Но отказоустойчивость, ради которой бонд и собран, наполовину выключена: упадёт `veth2-peer`, и переключаться будет не на что. Такое можно возить в проде месяцами и узнать в момент отказа. Ни один функциональный тест этого не находит, только сравнение с эталоном.

## Что осталось в бэклоге

- **Добавить MTU интерфейсов в эталон.** Этот прогон показал, что дрейф MTU накапливается незамеченным (см. поломку 2).
- Сузить DNAT-правило по `ip daddr` (см. поломку 5).
- Дубли правил в цепочках `forward` и `postrouting` — накопились при сборке стенда, на работу не влияют, но засоряют эталон.
- Стенд поднимается bash-скриптами (`restore-stand.sh`, `setup-office.sh`). Следующий шаг — переписать на Ansible, чтобы состояние было декларативным, а не восстанавливаемым вручную.
