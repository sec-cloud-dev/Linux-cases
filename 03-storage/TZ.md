# ТЗ — блок 3: хранилище под базу результатов сканера

## Задача

Собрать на сервере отказоустойчивое зашифрованное хранилище под PostgreSQL, в которой bucket-scanner хранит результаты сканов. Бэкапы — по снапшотам, с историей, с доставкой в офисный сегмент по сети. Стенд переживает перезагрузку и отказ диска без ручных команд — кроме физической замены диска.

Связь с прошлыми блоками:

- блок 1 — права, SGID, ACL, sudoers, chattr, inode;
- блок 2 — тот же сетевой стенд: br-office, office1, nftables с policy drop.

## Условия

- Запись одним дублем на каждую из трёх частей: сборка, бэкап и восстановление, перезагрузка. Внутри части — без склеек; вырезаются только паузы.
- Свои шпоры по синтаксису можно. Подсказки — нельзя.
- Диски — шесть дополнительных виртуальных дисков по 2 ГБ в VirtualBox (sdb–sdg). Loop-устройства не годятся: они не переживают перезагрузку, а перезагрузка — часть приёмки.
- Стенд блока 2 остаётся рабочим: `verify.sh` блока 2 не даёт новых FAIL по сравнению с текущим состоянием.

## Целевая схема

```
sdb sdc sdd sde  ──►  RAID-10  /dev/md/data      (+ sdf — hot spare)
                          │
                        PV → VG vg_data
                          ├─ lv_db    1,5 ГБ → LUKS2 → ФС → каталог данных PostgreSQL
                          ├─ lv_logs  1 ГБ   → ext4 с плотными inode → /srv/scanner
                          └─ свободно не меньше 20% VG — под снапшоты

sdg  ──►  отдельная ФС → /backup    (бэкапы базы + бэкап заголовка LUKS)
                          │
                        NFS, read-only ──► office1 через br-office
```

## Требования

### 1. RAID

1.1. RAID-10 из четырёх дисков, пятый — hot spare.

1.2. Массив собирается при загрузке сам, и ссылка `/dev/md/data` всегда указывает на него. Номер ядра (`md127` или другой) может быть любым — стабильным должно быть имя `/dev/md/data`.

1.3. При отказе диска массив сам подхватывает spare и ребилдится; событие попадает в журнал.

### 2. LVM

2.1. PV на массиве, VG `vg_data`, тома по схеме выше.

2.2. В VG остаётся не меньше 20% свободных extent'ов — под снапшоты.

2.3. На видео: `lv_logs` расширяется на 200 МБ на живой системе, во время записи в него, без отмонтирования.

### 3. Шифрование

3.1. LUKS2 только на `lv_db`. В README — почему остальные тома не шифруются.

3.2. Два слота: парольная фраза и файл-ключ. В README — где лежит файл-ключ, от какой угрозы шифрование при этом защищает и от какой нет.

3.3. Бэкап заголовка LUKS лежит на `/backup`, не на массиве.

3.4. Том открывается при загрузке автоматически.

### 4. Файловые системы и монтирование

4.1. ФС под базу — ext4 или XFS. В README — обоснование выбора: сжатие, inode, характер нагрузки.

4.2. `lv_logs` форматируется с расчётом на большое число мелких файлов. Плотность inode задана явно и обоснована.

4.3. Всё монтируется по UUID. Опции: `noatime` там, где это безопасно; `nosuid,nodev` на всех томах данных; `noexec` на `lv_logs` и `/backup`.

4.4. `nofail` стоит там, где отсутствие тома не должно ронять загрузку, и не стоит там, где должно. В README — решение по каждому тому и почему.

4.5. `/tmp` — tmpfs с ограничением размера.

### 5. База

5.1. PostgreSQL, каталог данных на томе с LUKS.

5.2. Каталог данных: владелец `postgres`, права `0700`. Других пользователей на этом томе нет.

5.3. Таблица под результаты сканов, тестовые данные загружены.

### 6. Права и пользователи

6.1. Каталог `/srv/scanner/reports` для группы `scanner`: новые файлы автоматически получают группу `scanner` и групповые права на чтение и запись.

6.2. Контейнер bucket-scanner пишет отчёты в `/srv/scanner/reports` через bind mount, и файлы получают правильную группу. В README — как сопоставлены UID внутри контейнера и на хосте.

6.3. Пользователь `auditor` читает отчёты через ACL — без изменения классических прав и без членства в группе `scanner`. Это действует и для новых файлов.

6.4. Сервисный пользователь `backup` запускает бэкап без пароля, но через sudo ему разрешены только конкретные команды, нужные скрипту. Не `ALL`.

6.5. Файл-ключ LUKS защищён от удаления и изменения, в том числе от root по ошибке.

### 7. Бэкап и восстановление

7.1. Скрипт `/usr/local/bin/db-backup.sh`: снапшот `lv_db` → открыть и смонтировать read-only → rsync с `--link-dest` в `/backup/db/<дата>` → отмонтировать → закрыть → удалить снапшот.

7.2. Если скрипт падает на середине, снапшот всё равно удаляется. Проверяется намеренным обрывом скрипта.

7.3. Снапшот снимается во время записи в базу: в соседнем окне скрипт в цикле вставляет строки.

7.4. На видео: бэкап разворачивается в отдельный каталог, на нём поднимается второй экземпляр PostgreSQL на другом порту, данные читаются. В README — почему снапшот работающей базы оказался целостным.

7.5. Хранится 7 последних бэкапов, старшие удаляются. Через `du` показать, что неизменённые файлы занимают место один раз.

7.6. Запуск по расписанию — пока через cron. На `systemd.timer` перевести в блоке 4.

### 8. Доставка в офис

8.1. `/backup` экспортируется по NFS только в `10.0.0.0/24`, read-only, с `root_squash`.

8.2. В nftables NFSv4 (2049/TCP) разрешён в `input` только с `br-office`. Политика `drop` сохраняется.

8.3. Клиент — неймспейс `office1`. Трафик идёт через `br-office`. Примечание по окружению: монтирование из неймспейса делается через `nsenter --net=/run/netns/office1` — сетевые запросы идут из `office1`, а точка монтирования видна хосту.

8.4. На видео: root из `office1` не может прочитать файл, который на сервере доступен только root. `ls -ln` на сервере и на клиенте показывает, на какой UID подменился root.

### 9. Перезагрузка — главная приёмка

9.1. После обычной перезагрузки без единой ручной команды: массив собран как `/dev/md/data`, VG активен, LUKS открыт, всё смонтировано, PostgreSQL работает, NFS отдаётся, стенд блока 2 жив.

9.2. Перезагрузка с отключённым диском массива: система загружается, массив работает в деградированном режиме, spare уходит в ребилд, после ребилда массив снова полный.

### 10. Проверка и эталон

10.1. `verify-storage.sh` по образцу блока 2: функциональные проверки плюс дифф против снимков в `etalon/`.

10.2. В эталон входят: `lsblk -f`, состояние массива (без счётчиков событий), `pvs`/`vgs`/`lvs`, слоты LUKS, опции монтирования из `findmnt`, `fstab` и `crypttab`, `getfacl` на каталоги отчётов, атрибуты файла-ключа, `sudo -l -U backup`, `exportfs -v`, ruleset nftables.

## Критерии приёмки

1. `verify-storage.sh` — ни одного FAIL. `verify.sh` блока 2 — ни одного нового FAIL.
2. Перезагрузки 9.1 и 9.2 пройдены на видео.
3. Восстановление из бэкапа 7.4 пройдено на видео.
4. В README объяснены все решения, помеченные «в README».

## Усложнения — по желанию

- WAL базы на отдельном томе. Снапшоты двух томов тогда не атомарны — добиться целостного бэкапа и объяснить как.
- Замена всех четырёх дисков массива на диски большего размера по одному, без остановки базы, с ростом массива, PV, LV и ФС.
- Смена мастер-ключа LUKS на живом томе.

## Трабалшутинг — вторая часть

Отдельное ТЗ после сборки, по образцу блока 2: скрипт вносит случайные поломки, чинить вслепую до полного совпадения с эталоном.

Кандидаты в пулы поломок:

- отказ диска; два отказа в одной паре
- массив собрался как `md127`
- ошибка в `fstab` — загрузка в emergency
- нет файла-ключа — загрузка ждёт пароль
- переполнение снапшота во время бэкапа
- кончились inode на `lv_logs` при свободном месте
- удалённый, но открытый процессом файл держит место
- после пересоздания ФС сменился UUID
- сломаны SGID или ACL — отчёты сканера с чужой группой
- сломан sudoers у `backup` — бэкап не идёт
- атрибут неизменяемости мешает правке
- nftables режет 2049
- права на экспорте и `root_squash`
