# ТЗ — трабалшутинг блока 3

## Задача

Две части на собранном стенде блока 3.

1. **Вслепую.** Скрипт вносит 9–10 поломок по всем восьми слоям хранилища, часть из них стоит друг на друге. Найти все, починить, вернуть стенд к эталону и доказать, что он переживает перезагрузку.
2. **Сервер не грузится.** Две поломки загрузки по очереди: одна при заблокированном root, другая — при root с неизвестным паролем. Поднять сервер с консоли.

## Условия

**Вслепую.** Скрипт `break-storage.sh` (на стенде — `/root/storage/`) выбирает набор случайно и ничего не выводит, кроме итоговой строки. Запускается в начале записи, в кадре. Набор неизвестен ни до решения, ни во время.

**Одна запись, без вырезок.** Каждая часть — отдельная запись одним куском, без склеек. Если дубль срывался, стенд откатывался на снапшот, и скрипт заново выбирал поломки, поэтому опубликованные записи тоже вслепую. Вторая запись начинается с результата `verify-storage.sh` на экране: стенд в эталоне после первой части. Между записями на него добавлены только скрипты части 2 и drop-in строгой загрузки (см. «Особенности стенда»). На монтаже не вырезается ни одной секунды: паузы и долгие ожидания (ребилд, перезагрузка) только ускоряются, скорость подписана на экране. Непрерывность видна в самой записи: один файл без склеек, время в журнале сервера (запуск скрипта, перезагрузка) совпадает с таймлайном видео, а курсор терминала при потере фокуса становится контурным — переключение на другое окно было бы видно.

**Свои шпоры можно, подсказки нельзя.** Разрешены заранее подготовленные заметки по синтаксису. Запрещено обращаться за диагностикой к кому-либо.

**`verify-storage.sh` — только для приёмки.** Во время поиска его не запускать: поломки ищутся по симптомам и по слоям снизу вверх (диски → RAID → LVM → LUKS → ФС → сервисы → права → бэкап), как на сервере, где такого скрипта нет.

## Часть 1 — вслепую

Скрипт вносит по одной случайной поломке на каждый из восьми слоёв и ещё одну — на одном или двух случайных слоях, всего 9 или 10. Условия набора:

- хотя бы две поломки проявляются только после перезагрузки: до ребута всё работает;
- хотя бы одна пара стоит друг на друге: вторую не видно, пока не починена первая (например, ФС-поломка на томе, который выключен в LVM);
- несовместимые пары исключены: те, где одна поломка поглощает другую, и те, что вместе ломают стенд без возврата.

| Слой | Варианты |
|---|---|
| Диски | активный диск пропал с шины |
| RAID | spare вынут из массива, и сбойнул активный диск · spare сбойный, но так и висит в массиве · скорость ребилда задушена |
| LVM | забытый ручной снапшот съел свободное место в VG · LV с логами выключен |
| LUKS | удалён слот с файлом-ключом **[ребут]** · опечатка в пути к ключу в `crypttab` **[ребут]** · в `crypttab` том открывается только на чтение **[ребут]** · том переоткрыт только на чтение · затёрт заголовок LUKS |
| ФС | на `/backup` кончились inode · процесс держит удалённый файл, `/backup` заполнен · том логов забит дампом памяти · том логов перемонтирован только на чтение |
| Сервисы | права каталога данных PostgreSQL **[ребут]** · кластер PostgreSQL не стартует при загрузке **[ребут]** · NFSv3 снова включён в `nfs.conf` **[ребут]** · NFS-сервер не стартует при загрузке **[ребут]** · PostgreSQL слушает не тот порт · база упала |
| Права | маска ACL на каталоге отчётов · сменена группа каталога отчётов · сменён владелец лога сканера · у владельца лога снята запись |
| Бэкап | sudo не читает правило для `backup` · cron игнорирует файл задания · cron остановлен и выключен · в расписании дата, которая не наступит · скрипт бэкапа не исполняемый |

**[ребут]** — до перезагрузки симптомов нет.

Итого **254 268 наборов** из 30 поломок. Диск, который пропадает или сбоит, выбирается случайно, но так, чтобы у RAID-10 осталась целая копия каждой зеркальной пары.

Ошибки внесения пишутся в `/root/.b3/err`; если файл не пуст, скрипт печатает их вместо «внесено поломок: N» — защита от поломки, которая не внеслась и которую искали бы впустую. Каждая поломка проверяется после внесения по результату (диск помечен faulty, слот удалён, файл изменён), а не по коду возврата. Перед внесением скрипт сверяет стенд с эталоном и откажется работать, если стенд уже не в эталоне.

**Приёмка:** `verify-storage.sh` без FAIL → перезагрузка → снова без FAIL.

## Часть 2 — сервер не грузится

Поломки загрузки, по одной на подчасть, порядок случайный:

- в `mdadm.conf` чужой `ARRAY` и `AUTO -all`, initramfs пересобран — после ребута массив не собирается;
- в `fstab` у `/backup` сбит UUID и убран `nofail`.

**2а — root заблокирован** (как на стенде, `passwd -S root` → `L`). Вход — emergency shell. В Ubuntu `sulogin` при заблокированном root пускает без пароля по Enter.

**2б — root с неизвестным паролем** (имитация: пароль задал предыдущий админ). Emergency спросит пароль, которого нет. Вход через GRUB: при старте держать Shift → `e` → в строку `linux` дописать `init=/bin/bash` → Ctrl+X → `mount -o remount,rw /` → `passwd -l root` → `exec /sbin/init`. Root снова заблокирован, и загрузка приходит в emergency, как в 2а. В конце root должен быть заблокирован — это проверяет `verify`.

**Вход — только с консоли VM, починка — по SSH.** Ctrl+D в emergency (продолжить загрузку мимо ошибки) не используется: он обходит и поломку, и неизвестный пароль. Из emergency shell SSH поднимается одной командой — `systemctl start --job-mode=ignore-dependencies ssh systemd-user-sessions`, — дальше работа идёт в обычном терминале. `ignore-dependencies` нужен потому, что `sysinit.target` на стенде упал (см. «Особенности стенда»), а `ssh` от него зависит; `systemd-user-sessions` убирает `/run/nologin`, иначе `pam_nologin` не пустит обычного пользователя, а root по SSH не входит.

Поломки вносят два скрипта в `/root/storage`: `boot-2a.sh` (первая, root остаётся заблокированным) и `boot-2b.sh` (вторая, только после починенной первой; root получает случайный пароль). Оба — обёртки над `break-storage.sh --boot`.

**Приёмка:** после каждой починки сервер грузится сам и `verify-storage.sh` без FAIL. После 2а это же проверяет `boot-2b.sh`: на стенде не в эталоне он не запустится.

## Что считается решённым

1. `verify-storage.sh` — ни одного FAIL до и после перезагрузки.
2. Каждая поломка в разборе имеет причину, а не только фикс: недостаточно «вернул слот», нужно объяснить, почему без него ломалось именно то, что ломалось, и почему до перезагрузки этого не было видно.

## Эталон и проверки

`verify-storage.sh` — 51 функциональная проверка и дифф 12 снимков с эталоном в `/root/etalon/storage` (`--etalon` снимает заново).

Диски в эталоне записаны по серийникам, массив — как `md/data`: буквы `sdX` и номер `mdNNN` зависят от порядка, в котором ядро нашло диски. Состав массива сверяется как набор дисков без привязки к слотам: после ребилда бывший spare становится активным, это не расхождение — число активных и spare сверяется по заголовку `mdadm --detail`.

| Снимок | Что фиксирует |
|---|---|
| `lsblk` | дерево устройств, ФС, UUID, точки монтирования |
| `md` | заголовок массива без счётчиков событий + набор дисков |
| `lvm` | `pvs`, `vgs`, `lvs` |
| `luks` | список слотов |
| `mounts` | опции монтирования из `findmnt` |
| `fstab` | `fstab` и `crypttab` |
| `acl`, `attr` | ACL каталога отчётов, атрибуты файла-ключа |
| `sudo`, `nfs`, `nft` | `sudo -l -U backup`, `exportfs -v`, ruleset |
| `conf` | `mdadm.conf`, `nfs.conf`, права файлов в `cron.d` и `sudoers.d`, файл задания cron побайтно, `start.conf` кластера, контейнер, владельцы и права каталогов сканера, лога и скрипта бэкапа |

Проверки, добавленные под трабалшутинг: нет сбойных дисков в массиве; скорость ребилда — по умолчанию; `ARRAY` в `mdadm.conf` — этот массив; `mdadm.conf` в initramfs совпадает с `/etc`; ключ из `crypttab` существует и открывает том; бэкап заголовка LUKS содержит оба слота; `findmnt --verify` без ошибок; место и inode на томах < 90%; нет удалённых, но открытых файлов; в VG нет снапшотов; `start.conf` = `auto`; кластер на порту 5432; `vers3 = n` в `nfs.conf`; `nfs-server` в автозапуске; сканер пишет лог (последняя запись < 60 с назад); cron работает и в автозапуске; файл задания cron — `root 644` с переводом строки в конце; скрипт бэкапа — `root 755`; root заблокирован.

Снимок `conf` с правами каталогов ловит и лишние правки: если при починке открыть доступ шире, чем было, или сменить группу каталога, который не ломали, приёмка не пройдёт.

## Особенности стенда

- **Пароль LUKS при загрузке.** Если файл-ключ не открывает том, загрузка спрашивает пароль слота 0 на консоли. На ввод — 90 секунд: столько монтирование ждёт устройство, дальше emergency mode.
- **Строгая загрузка.** В Ubuntu `sysinit.target` только хочет (`Wants`) `local-fs.target`, поэтому при упавшем монтировании обычная загрузка гонится с emergency: на таймауте 90 с она успевает дойти до `multi-user.target` (проверено: `sysinit.target` достигнут на 0,04 с раньше старта `emergency.service`), сама гасит emergency и поднимает SSH — сервер «грузится» с поломкой. На стенде стоит drop-in `/etc/systemd/system/sysinit.target.d/10-strict-local-fs.conf` с `Requires=local-fs.target`: упало локальное монтирование — `sysinit.target` падает следом, загрузка детерминированно стоит в emergency.
- **Меню GRUB скрыто** (`GRUB_TIMEOUT_STYLE=hidden`, таймаут 0). Открывается, если держать Shift при старте VM.
- **Контейнер сканера при загрузке перезапускает `stand-net.service`** из блока 2 — политика рестарта контейнера на загрузку не влияет.
- `verify-storage.sh` работает ~15 секунд: распаковывает initramfs, чтобы сверить `mdadm.conf`.
